## 1. 目标、验收与边界

- 原始目标：帮助用户聚焦复杂技术问题，隔离探索、比较取舍，形成有证据、可交接的决策。
- 首期验收：在同一主会话完成“目标与约束 → 分支探索 → 方案比较 → 人工采纳 → Markdown 交接”，刷新后可恢复已保存内容。
- 改动边界：Web Chat、最小决策领域模型与持久化、API/SDK、相关上下文与验证；本轮只交付方案。
- 非目标：重写执行引擎、通用项目管理平台、自动多 Agent 扇出、自动编码交付、浏览器平台、长期记忆重构、Android 原生运行时同步实现。
- 下一步：先冻结首期数据/API 契约，再并行开发独立模块；另一个会话承担的基础修复不在这里重复实施。

产品定位：**面向复杂技术问题的方案探索与决策 Agent**。衡量的是决策质量与用户注意力成本，不是报告长度、分支数量或 Agent 数量。

## 3. 首期产品闭环

在现有 Chat 内增加“方案”面板，不新增一级平台入口。首期一个 root thread 对应一个决策工作区；普通聊天不自动创建工作区。

```text
用户确认目标/约束/比较标准
          ↓
按需创建或打开现有分支 ──→ 绑定研究问题、预期证据、停止条件
          ↓                                  ↓
方案面板 ←──── 用户选入相关结论/证据 ←──── 分支调研
          ↓
同标准比较 → 人工确认选择与风险 → 固定版本 Markdown 交接
```

### 3.1 主面板

- 顶部只显示目标、硬约束、当前待决问题与下一步；详细来源按需展开。
- 比较区按统一 criteria 展示选项，允许“不改动”和“最小改动”；不强制虚构三个方案。
- 关键判断区分事实、用户约束、假设、建议。缺少支持时显示“待验证”，不是补一个看似精确的置信分数。
- 用户在需要时点击“继续探索”“纳入比较”“确认选择”“导出交接”。模型只提出候选，不自动确认。
- 手机窄屏使用现有抽屉/标签页交互，避免同时展示完整聊天、分支树、矩阵三列。

前端接线点为 [thread-page.tsx](../../../apps/web/src/pages/thread/thread-page.tsx) 与 [thread-page-content.tsx](../../../apps/web/src/pages/thread/thread-page-content.tsx)。复用 [branch-tree-panel](../../../apps/web/src/features/branch-tree/branch-tree-panel.tsx) 导航；借鉴 [merge-review-sections](../../../apps/web/src/features/merge-review/merge-review-sections.tsx) 的材料编辑交互，但不复用其批准动作来确认方案。SDK 现有分支调用位于 [thread-branch.ts](../../../frontend-sdk/src/client/thread-branch.ts)。

### 3.2 有目的的分支

分支绑定包含 `question`、`expected_evidence`、`stop_condition` 和可选 `option_id`。只有新信息可能影响决策才建议继续探索；这些字段首期是研究约束，不宣称已实现硬预算或自动停止执行。

复用现有 fork/open API，成功后再绑定工作区。绑定失败不自动重建或删除分支，用户可以重试绑定；首期不承诺 fork 与绑定跨存储原子提交。已合并或归档的同归属分支可提供历史证据，能否继续执行仍由原生命周期规则控制。

### 3.3 采纳与交接

“纳入比较”只是保存候选材料；“采纳方案”记录用户决定；“合并分支结论”仍是原功能。三者不得合并为一个隐式按钮。

交接包含：目标/非目标、硬约束、所选方案、未选方案及理由、证据、待验证假设、接受的风险、实施步骤、验收标准、重新讨论的条件。首期只下载或复制 Markdown，不替用户向另一个 Agent 发消息、不自动修改代码。

## 4. 最小技术架构

### 4.1 一个权威聚合，不另建执行系统

新增 `DecisionWorkspace`，由独立服务负责领域验证，数据库保存权威记录。graph 中仅保留本轮读取的上下文投影；模型、流式消息与摘要均不得回写覆盖用户确认的决定。

拟议结构（是一个聚合内的字段，不是每行新建一张表）：

| 字段 | 含义 |
| --- | --- |
| `root_thread_id / owner_user_id / revision` | 主线程归属；owner 从认证上下文注入；服务端递增版本 |
| `brief` | 目标、非目标、硬约束、待决问题 |
| `criteria[]` | 有稳定 ID 的统一比较标准，不默认使用加权总分 |
| `options[]` | 有稳定 ID 的方案、按 criterion 的判断、假设、风险、实施步骤与验收 |
| `evidence[]` | 来源种类、引用、定位、采集时间/可得来源版本、简短支撑内容、有效性说明 |
| `branch_bindings[]` | 已有分支 ID、研究问题、预期证据、停止条件、可选方案 ID |
| `decisions[]` | 人工决定 ID、选择、理由、接受风险、重开条件、确认者/时间，以及当时内容快照 |

不复制完整 transcript；不建设通用证据知识图谱。一个 URL 的存在不等于其支持某个判断，引用校验和语义支持度分开。

### 4.2 持久化与并发

建议新增一张 `focus_decision_workspaces` 聚合表：root 主键/唯一约束、owner、revision、data_json、created_at、updated_at。SQLite 和 PostgreSQL 使用各自现有连接与迁移方式，测试内存实现保持相同仓储契约。数据库版本号由集成人在落地时依据最新迁移序列分配。

不直接扩展 Team session 的 JSON：旧的无条件 `save_session` 可能绕开工作区 CAS 覆盖数据，而且会让普通 Chat 的方案能力耦合 Team 生命周期。新增一个小聚合表比改造所有 Team 写入口更窄。

- 新建只允许绑定已存在、当前用户拥有的 root；不能靠读操作自动认领未知线程。
- 更新要求 `expected_revision`，数据库执行带 owner/root/revision 条件的更新并原子递增；不是“先读版本，再无条件保存”。冲突返回 409，UI 保留本地输入供用户处理。
- 用户确认追加 decision 快照与 revision 更新在同一事务内完成。服务端生成确认人、时间与 ID，不允许客户端伪造。
- 草稿编辑不改历史确认快照；确认后改动显示“有未确认变更”，不能继续把旧选择呈现为当前草稿的有效确认。
- 网络响应丢失时先重读服务器版本判断结果；不自动用新 revision 重放一次用户确认。
- 保存后的工作区可在数据库重启后读取；**这不等于正在进行的模型任务支持进程崩溃续跑**。
- 工作区与会话的删除/用户数据删除路径一并覆盖，不能只删聊天而留下决策快照中的用户内容。

### 4.3 API 与 SDK 契约

下列是拟议接口，冻结后再开发；不改写现有 BranchDecisionEvent 的含义。

| 方法与路径 | 行为 |
| --- | --- |
| `GET /v1/threads/{root_thread_id}/decision-workspace` | 读取当前工作区；不存在返回 404，不隐式创建 |
| `PUT /v1/threads/{root_thread_id}/decision-workspace` | 创建或保存可编辑内容；创建约定 expected_revision=0，已存在则 409；后续更新必须匹配版本 |
| `POST /v1/threads/{root_thread_id}/decision-workspace/decisions` | 按 expected_revision 确认选择并固化快照；缺少必要理由/无有效 option ID 时拒绝 |
| `GET /v1/threads/{root_thread_id}/decision-workspace/decisions/{decision_id}/handoff` | 只读、确定性渲染已确认快照为 Markdown；不调用模型、不创建服务端任意文件 |

PUT 只接受草稿白名单字段，不能改 owner、revision 或历史 decisions。绑定分支、选项和证据可在同一次草稿更新中提交，无需首期为每个子对象建立 CRUD 路由。

所有操作先检查 principal 和根线程 owner，再读取可能触发图状态回填的路径。每个内部来源引用必须验证 owner 与工作区 root 关系；首期不做跨项目引用。外部链接只当引用显示，不能把导出接口变成任意 URL 抓取或任意服务端路径下载。

OpenAPI 是 SDK 类型的来源；禁止前后端分别手写两份最终契约。接口注册、生成契约文件和 SDK 生成输出由一个集成 writer 管理。

### 4.4 Agent 如何参与，而不只是一个手工表单

首个纵向切片允许人工输入，随后补齐以下模型辅助，二者共同构成首期完整交付：

1. 主线程每轮按需读取已保存 brief、最新确认决策、未决问题；分支只得到 brief 与自身研究绑定。利用现有上下文装配入口，避免全矩阵、所有分支全文重复注入。
2. 固定本轮读取的 revision；运行中用户编辑不改变该轮输入，输出标记基于的 revision。过时结果可查看，但不能静默覆盖新草稿。
3. 复用普通 Chat/已有调研工具辅助提出方案、比较判断和下一步。首期从回答或 MergeProposal 明确“纳入比较”，展示编辑预览，由用户保存；不用解析任意自由文本后自动更新工作区。
4. 不新增后台调研队列或无人值守循环。外部网页和分支内容作为待分析数据，不能改变权限、确认决定或触发隐藏写操作。
5. 若实际交互证明手工选入成本过高，再增加严格校验的结构化候选输出；不把它当作本轮的新工具执行协议。

## 5. 多 Agent 开发组织

这里区分“使用多个 Agent 开发本产品”和“产品内部自动运行多个 Agent”。前者现在采用，后者不是首期前置条件。

### 5.1 角色、文件所有权与交付

主 Agent 负责契约、公共文件、集成与最终验收；最多同时运行三个独立子任务。下列角色按阶段复用槽位，不要求一次启动所有角色。

| 工作包 | writer 与范围（拟议新文件；现有路径按落地核对） | 验收输出 |
| --- | --- | --- |
| W0 契约冻结 | 主 Agent：领域字段、API 示例、错误语义、输入边界、首期样例；共享契约文件 | 一份前后端共用 fixture，明确 owner/CAS/快照语义 |
| W1 领域/仓储 | 后端 Agent：`core/decision_workspace.py`、对应 repository 实现及契约测试 | owner 隔离、CAS、确认事务、重启读取；提供迁移片段，主 Agent 合入共享迁移文件 |
| W2 前端 | 前端 Agent：`apps/web/src/features/decision-workspace/`，独立组件/状态与组件测试 | 用 W0 fixture 完成比较、冲突、确认、导出交互；不自行改 SDK 生成文件 |
| W3 验收样例 | 验证 Agent：独立测试数据、场景脚本、产品对照评估说明 | 正常闭环及越权、并发、过时输出、未验证假设等验收样例 |
| W4 服务/API/SDK 接线 | W1 后由后端 Agent 实现服务/路由；主 Agent 管理 runtime 装配、路由注册、OpenAPI/SDK 生成 | HTTP 行为测试与真实 SDK transport 测试 |
| W5 上下文接线 | 可复用已空闲 Agent：授权后读取 workspace、有限上下文投影与来源 revision | 主线程/分支上下文隔离，旧输出不覆盖草稿 |
| W6 集成与审查 | 主 Agent 整合；验证 Agent 只读审查最终差异及证据 | 浏览器闭环、相关回归、缺陷修复与当前文档更新 |

依赖关系：

```text
W0 → W1 ──→ W4 ──┐
   → W2 ──────────┼→ W6
   → W3 ──────────┤
        W1 → W5 ──┘
```

W2 可先用同契约 fixture，不等后端实现；不能以 mock 页面通过替代最终真实 API 验收。W4 与 W5 的 runtime 公共装配由主 Agent 串行合入。

### 5.2 协作约束

- 优先复用现有原生子 Agent；实现阶段每个 writer 使用独立 worktree/分支，或在共享树中明确互斥文件所有权。不得并行切换共享分支。
- `runtime` 装配、API 合同注册、schema migrations、生成 SDK、Makefile、文档索引是共享热点，由主 Agent 或指定唯一 writer 修改。
- 每次委派包含目标、允许写路径、不得修改路径、输入契约、验收命令、交付证据和已知依赖。交接返回实际 diff、测试结果、未决风险，不只说“完成”。
- 不预先永久绑定模型品牌。实施派发时使用实际可调用且满足任务要求的模型，记录实际模型与能力限制；模型不可选时明确继承会话模型，不能声称完成指定模型路由。
- 领域契约和安全边界由主 Agent 判断；独立验证不依赖实现 Agent 的自我确认。只修复有具体失败路径的 finding，不递归创建评审流程。
- 与已有修复会话以实际提交/可审查补丁为交接点，不以另一个会话口头“已完成”为合并依据。未提交共享改动不得覆盖或打包进新任务提交。

## 6. 实施顺序与基础修复关系

### M1：可持久保存的手工决策闭环

交付 W0–W4：方案面板、目标与比较、用户绑定现有分支、人工确认、固定快照 Markdown 导出。此阶段不要求自动生成结构化矩阵。

### M2：Agent 辅助闭环与首期发布

完成 W5–W6：模型可理解当前目标与已确认选择，用户可将调研结果选入比较；主线程和分支上下文正确隔离；真实浏览器从创建到交接完整验收。M1 是可演示中间产物，不能单独宣称方案 Agent 已完成。

### M3：有证据再增加自动协作

只有真实任务证明分支研究可独立且人工操作构成瓶颈，再接 Team 自动调研、结构化候选和有界返工。届时另验预算、取消、审批、恢复，不把当前规划接口当成生产就绪执行器。

| 既有问题/能力 | 对本方案的影响 |
| --- | --- |
| owner 检查晚于读取/回填 | 所有新路径必须先授权；若上下文接线复用问题路径，其修复是接线发布前置，不阻塞独立 UI/仓储开发 |
| SDK 构建产物过时 | SDK transport/流式回归之前先构建，不能误判新功能失败 |
| 分支 handoff/操作卡问题 | 涉及的新按钮和导航必须覆盖行为测试；无关操作不纳入本轮清理 |
| 运行恢复、follow-up、Team 审批续跑、真实预算 | 人工触发普通交互的首期无需等待全部完成；也不能因此承诺无人值守持续研究 |
| 退出信号、readiness、部署重启策略 | 部署可靠性由原修复线处理；正式服务发布需核验所选部署路径，不宣称文档等于修复 |
| 浏览器、全量连接器、复杂长期记忆、通用任务中心 | 不进入首期依赖链 |

## 7. 验收设计

### 7.1 必须通过的行为

1. 用户从主会话创建工作区，记录目标/约束，关联两个已有分支，以相同标准比较选项，确认选择并导出包含理由、证据、未知项和验收条件的 Markdown。
2. 页面刷新和服务正常重启后，已保存草稿及确认快照一致；不把此测试解释为运行中模型任务可恢复。
3. 另一用户不能读、改、确认、导出，也不能引用越权分支/产物；拒绝之前无 owner 回填、图更新或记忆写入。
4. 两次同 revision 更新仅一次成功；失败方看到 409 并保留输入。后返回的模型结果不得覆盖已更新草稿。
5. 确认方案不自动调用 merge，不修改主线程 imported findings/长期记忆，不把假设改成事实；原显式 merge 行为保持兼容。
6. 确认后修改约束，UI 标记未确认变更；历史决策仍导出原快照，不能拼接新草稿伪装成当时结论。
7. 缺失证据可记录为待验证；无证据的判断不能显示为已验证。来源内容变动/不可访问时保留捕获信息并提示适用性未知，而非虚构实时有效性。
8. 未开启方案面板的普通聊天、既有分支导航与合并不被强制迁移。宽屏与窄屏的键盘操作、焦点和错误提示可用。
9. 删除相关用户数据时处理工作区与决策快照；导出不读取任意本地路径，不执行来源内指令。

### 7.2 最小工程验证集

- 新增仓储契约测试覆盖内存/SQLite；PostgreSQL 集成环境验证真实条件更新、事务和迁移，不用内存锁测试代替数据库并发证明。
- 新增 service/API 测试覆盖上述 owner、版本、确认快照与引用边界；对应命令按最终测试文件名确定，不提前声称文件已存在。
- 前端组件测试覆盖矩阵未知项、冲突保留输入、过时建议和确认快照；真实浏览器 smoke 使用真实 API 完成第 1 项。
- 契约/接线变更后执行相关的 `make contract-check`、`make sdk-check`、`make web-check`；SDK transport 及依赖 dist 的回归前执行 `make sdk-build`。
- 若修改分支/流式调用路径，再运行相应现有回归；不因本方案而默认执行整个历史评测集。
- 既有 eval 中 final state 回退初始状态、acceptance 未强制等问题修复前，不用其绿色结果证明新能力；首期直接断言真实最终持久化状态和 API 结果，不为接入旧评测框架扩张产品前置工作。

### 7.3 验证产品价值

用同一模型、相同初始材料与相近预算，比较普通线性聊天和方案工作区；先取少量真实的技术选型、设计评审、改造规划任务做配对试验，不把小样本包装成统计结论。

记录用户恢复上下文的时间、关键约束遗漏、关键判断的证据支持、执行方补问次数和交接后的返工。模型辅助评分只作线索，关键证据支持与遗漏由人工核对。只有质量不下降且注意力成本下降，才扩大自动协作与产品入口。

## 8. 发布、回退与完成条件

方案能力使用一个明确的服务端能力开关控制 UI/API 暴露；普通聊天默认语义保持不变。首期支持现有服务端 SQLite/PostgreSQL 剖面，Android 设备本地 runtime 不宣称同步支持。

迁移采用新增表，不重写既有会话。关闭功能停止新写入并隐藏入口，不自动删除已保存决策；删除仍走明确数据删除流程。回退版本需核对保留新表的兼容性，不能靠删表回退。

完成条件：M2 的真实闭环、权限/并发/快照行为及受影响回归通过，已知限制可见，现状文档据实际实现更新。到此结束首期，不顺手扩成项目管理、文件平台或自主编码系统。
